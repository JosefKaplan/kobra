# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Czech-language Nette 3 web application ("Kobra"): user management + login/registration on the front, and a small CMS (pages composed of typed components) in an admin section. PHP ≥ 8.2, MariaDB 10.6+ (deployment target; 10.11 LTS recommended — MySQL 8 also works), database `kobra`, Doctrine ORM via Nettrine, Latte templates, Bootstrap 5 + Contributte Datagrid v7, Vite + Sass for assets. All UI copy is Czech; keep new user-facing strings Czech. `parameters.database.serverVersion` in `config/common.neon` (overridable in `config/local.neon`) picks the Doctrine platform — must match the real server (`'10.11.x-MariaDB'` vs `'8.0'`); the `-MariaDB` suffix is what selects MariaDBPlatform. See `config/local.neon.example`.

## Commands

```bash
composer install                 # PHP deps
npm install                      # JS deps
npm run build                    # build assets into www/assets/ (gitignored — must build after clone)
npm run dev                      # Vite dev server (assets served with HMR)
php -S localhost:8000 -t www     # run the app (needs MariaDB/MySQL running)

composer phpstan                 # static analysis, level 6, phpstan.neon (must stay clean)

php bin/console migrations:migrate --no-interaction   # apply DB migrations (also seeds the default admin account)
                                 # Single MariaDB-native baseline (Version20260904120000) — it squashes the
                                 # earlier MySQL-8 baseline + the spacing_top/spacing_bottom follow-ups; older
                                 # incremental history (incl. dropped component-type conversions) is in git only.
php bin/console migrations:diff  # generate migration after editing app/Entity/*
php bin/console orm:validate-schema
```

There is no test suite yet (`composer tester` expects a `tests/` dir that doesn't exist). Verify changes by running the app; default account after migrations: `admin`/`Admin123` (role admin; change the password right after a deploy) — no seeded plain-user account.

DB credentials live in `config/common.neon` (`parameters.database`, defaults root/root). Machine-specific overrides go in `config/local.neon` (gitignored, loaded automatically by `Bootstrap` if present).

## Architecture

Two Nette modules mapped in `config/common.neon` (`App\Modules\{Front,Admin}\**Presenter`), each directory holds presenter + its `.latte` templates side by side, with a module-level `@layout.latte` and `BasePresenter`.

- **Front** (public): `Home`, `Page` (renders CMS pages by `link` — the page's URL path segment), `Auth` (login/registration/logout). `Front\BasePresenter` injects `PageManager` and puts visible pages into `$navPages` in `beforeRender()` (used only by the fallback homepage's page grid — the navbar never lists pages automatically).
- **Admin** (requires login): `User` (datagrid CRUD), `Page` (datagrid + component editor), `Layout` (datagrid CRUD of reusable navbars/footers), `Menu` (datagrid CRUD of reusable link menus). `Admin\BasePresenter.startup()` redirects anonymous users to login with a `backlink` (request is restored after login). Admin `PagePresenter`, `LayoutPresenter` and `MenuPresenter` additionally require the `admin` role; `UserPresenter` does per-action role checks (a plain user may edit only their own profile).

Routing (`app/Core/RouterFactory.php`): `admin/<presenter>/<action>[/<id>]` for Admin; on Front, `<link>` maps single-segment URLs to `Page:default` **before** `<presenter>/<action>` — so any one-segment URL is treated as a CMS page link (e.g. `/auth` never reaches AuthPresenter; `/auth/login` does). "Link" (`pages.link`, `Page::$link`) is what other CMSs call a slug — a webalized single path segment, auto-generated from the title when left empty.

Data layer: Doctrine entities in `app/Entity/` (attribute mapping), thin service classes in `app/Models/` (`UserManager`, `PageManager`, `LayoutBlockManager`, `MenuManager`, `LoginLogManager`) that own all EntityManager access — presenters never touch the EM directly. Users are soft-deleted (`deletedAt`); every query in `UserManager` filters `deletedAt IS NULL`. Pages, page components, layout blocks and menus carry history/audit columns via the `App\Entity\AuditColumns` trait (`created_date`/`created_by`, `edited_date`/`edited_by`, `deleted_date`/`deleted_by`; the "by" fields are FKs to `users` with `ON DELETE SET NULL`) and are also soft-deleted: nothing hard-deletes them — `markDeleted()` stamps the row, every `PageManager`/`LayoutBlockManager` query filters `deletedDate IS NULL`, and the collection accessors (`getRootComponents()`, `PageComponent::getActiveChildren()`, `Page::getNavBlock()`/`getFooterBlock()`) skip deleted rows. The acting user comes from `Admin\BasePresenter::getUserEntity()`; presenters call `markCreated()`/`markEdited()`/`markDeleted()` explicitly. Caveat: `PageManager::linkExists()` deliberately counts soft-deleted pages too — their rows still hold the link under the DB unique constraint (auto-generated links get suffixed past them; explicitly entered ones error). `Authenticator` (app/Core/Security/) logs every attempt via `LoginLogManager`. Services are wired by convention in `config/services.neon` (`search:` registers `*Manager`, `*Factory`, … classes); presenters get dependencies via `#[Inject]` public properties.

### CMS component model

`Page` has ordered `PageComponent`s (cascade persist/remove, orphanRemoval). A component has a `type` string and a JSON `content` array. The nine types and their content keys are defined in **three places that must stay in sync**:

1. `Admin\Page\PagePresenter` — `handleAddComponent()` (default content) and `handleSaveComponent()` (whitelist/validation of posted keys). Components are ordered by `sortOrder` (the `OrderBy` mapping on `Page::$components`); `handleMoveComponent()` reorders via the up/down arrows in `edit.latte` and renumbers the whole sequence on every move.
2. `app/Modules/Admin/Page/edit.latte` — the editing form per type (plain HTML forms posting to the `saveComponent!` signal, not Nette forms)
3. `app/Modules/Front/components.latte` — the public renderer (`{switch}` per type), included by both `Page/default.latte` and (conditionally, for the selected homepage) `Home/default.latte`

Every component also carries `PageComponent::$spacingTop`/`$spacingBottom` — generic, type-independent overrides of the space above/below the block (`none`/`sm`/`lg`/`xl`, mapped to a CSS length by `PageComponent::SPACING_VALUES`). They're edited via the "Mezera nad blokem"/"Mezera pod blokem" selects in `_componentEditor.latte`'s shared form footer (alongside visibility — outside the per-type `{if}` block, so they apply to every type including `columns`), saved generically in `handleSaveComponent()` (not part of the per-type `content` whitelist), and applied in `components.latte` as one combined inline `style="margin-top: …; margin-bottom: …"` on each case's root element — inline style overrides the type's margin utility class regardless of specificity. The editor select has no blank "use type default" choice; `handleAddComponent()` sets both to `'sm'` explicitly for new components (the select shows "Malá" pre-selected), and `handleSaveComponent()` falls back to `'sm'` for anything unrecognized. `null` is still a legal DB value — meaning "fall through to the type's own hardcoded margin, no override" — but is now only reachable on components saved before this default existed; it stays that way until the component is next saved (which always writes a real value), so re-saving an old component silently switches it from its type's built-in margin to explicit `'sm'` unless another value is picked. Separately, `columns` children never get the type's built-in *top* margin (`heading`'s `mt-5`, `cta`'s `my-5`) — see `$isColumn` in `components.latte` — since it would sink them below siblings that have none, breaking the row's top alignment; an explicit `spacingTop` override still applies even to a column child.

Types: `hero`, `heading`, `text_block`, `image`, `columns`, `masonry` (+ its child-only `masonry_item`), `cta`, `contact_form`. When adding a type, update all three files plus the "Přidat blok" dropdown in `edit.latte` and the type-accent colors in `assets/scss/admin/_layout.scss`. Type notes: a `hero` with a non-empty `image_url` renders as a "cover" (photo + dark overlay + white text, `.page-hero-cover` in `assets/scss/front/_layout.scss`); a `heading` also emits its webalized text as its `id`, so nav links can target sections with `#latest-news`-style anchors (renaming a heading silently breaks such links); `image` is a URL-referenced `<figure>` (url/alt/caption); `masonry` is the second **container** type (see `columns` below): a grid of square image tiles framed by thin white lines (`$masonry-gap`, 3px, in `$masonry-gap-color` — used as the grid gap *and* the outer padding, so the outer edge is framed too) where every tile is a `masonry_item` child component (`content: {main_image_url, main_image_alt, heading, text, gallery: [{image_url, alt}, …]}`; visibility, order and audit come from the child row itself — `$isVisible`, `$sortOrder`, `AuditColumns` — not from JSON). Clicking a tile opens the tile's **"book" view**: a full-page Bootstrap modal (`modal-fullscreen`, `data-bs-backdrop="false"` — `$book-bg`, no dimmed backdrop; id = `masonry-item-<childId>`) laid out after pages 2–5 of the design: inside a `.book-frame` as wide as the grid, the main image (+ optional `heading`/`text`) hugs its photo on the left, capped to `--book-h` (viewport height minus the close-button gap and the arrow row), and the optional `gallery` sits right next to it in one narrow column (≤ 3 photos) or two (`$galleryCols` in Latte, `--gallery-cols` in CSS) whose width is `--book-col` = `min(18.6% of the frame, --book-h × .25)`, so the whole book fits a normal-height screen; gallery photos keep their own aspect ratio and are dealt left-to-right across the columns (admin order reads row by row). Below md it stacks: main image, then the gallery as a 2-column grid. A book taller than the viewport (always the case once stacked) scrolls the whole `.modal`: `.modal-dialog`/`.modal-content` grow with it (`min-height: 100%`, overriding Bootstrap's fullscreen `height: 100%`, which assumes a scrolling `.modal-body` the book doesn't have) — with the fixed height the overflow had no background and, with no backdrop, the page underneath showed through. The modal markup is a separate `{define masonryItemModal}` rendered by the `masonry` case *after* the grid, never inside `masonry_item` — `.page-masonry` breaks out of the 900px article via `margin-left: calc(...)` on purpose (not `transform`), because any transformed/positioned ancestor would become the containing block for the `position: fixed` modal and lay it out as another tile. The view has a thin SVG `.book-close` X top-right and thin SVG `<`/`>` `.book-nav` arrows in a `.book-navs` row at the bottom (both `$book-control` gray) (`data-masonry-nav="#masonry-item-<siblingId>"`, prev/next computed in Latte from the visible tiles, wrapping around; hidden when the masonry has a single tile). The book view's JS is all in `assets/front/masonry.js` (`initMasonryBooks()`, called from `front.js`). Gallery photos are `.book-thumb` buttons forming a mini gallery: a click swaps src/alt with the main photo (the old main photo becomes that thumbnail, so nothing is lost), pins the main block's width (`--book-main-w`, measured with the original photo) so the gallery doesn't move when a narrower/wider photo swaps in, replays a short fade via the `.book-swap` class, and scrolls the main photo into view (on phones it sits above the gallery); each swapped `<img>` keeps its original src/alt in `data-orig-src`/`data-orig-alt`, restored on `hidden.bs.modal` (which also unpins the width), so a book always reopens — or is paged back to — in its original order. Paging handles the arrows and the ←/→ keys — Bootstrap allows one open modal, so it hides the current one and shows the sibling on `hidden.bs.modal`, and, because the page would flash through in that gap, appends a fixed `$book-bg`-coloured `.book-stage` (`z-index: $zindex-modal - 1`) for the duration of the switch. Animations live in `_layout.scss` under `.masonry-book-modal`: opening scales the dialog from 96% (overriding Bootstrap's `.modal.fade` slide), paging slides the outgoing/incoming dialog sideways via the transient `data-book-leave`/`data-book-enter` attributes the JS sets and clears, and the main image/caption/gallery tiles fade up with a stagger driven by an inline `--i` on each gallery `<img>` (`$iterator->counter0`; like `--gallery-cols` on `.book-body`, a layout custom property set inline — fine, the no-hardcoded-colors rule is about colours); everything is disabled under `prefers-reduced-motion`. A `masonry_item` without a main image renders nothing. In the page editor the masonry card is compact (tile count + "Upravit dlaždice"); tiles are managed on `Admin:Page:masonry/<componentId>` (`actionMasonry` + `masonry.latte`, the masonry twin of `columns.latte`): one card per tile with its own `saveComponent!` form, the shared `componentHeader` (thumbnail of the main image, up/down arrows via `moveComponent!`, delete), "Přidat dlaždici" for an empty tile, and a bulk dropzone that creates one tile per dropped file — the files go through `uploadImage!` one at a time (see Image uploads) and the collected URLs are then POSTed to `createMasonryItems!(parentId)`, which appends one child per URL and redirects. A tile's gallery stays JSON inside the tile (a photo is just url+alt — a third entity level would be overkill, and containers deliberately don't nest). It's edited with the shared **editable image list** — `{define imageListEditor}` / `{define imageListRow}` in `_componentEditor.latte` (bulk dropzone + rows + "add empty row" + the row `<template>`), mounted by `masonry.js` on `[data-image-list]`, parametrised by the POST field name (`gallery[<index>]` here, `carousel[<index>]` for a footer block's carousel) and an optional link column (`withLink`): rows are added/removed/bulk-uploaded and reordered either by grip-handle drag or by the per-row ↑/↓ arrows (`data-gallery-item-move`) — both purely client-side DOM moves in `assets/admin/masonry.js`. The drag (`wireSorting()`) is deliberately **not** native HTML5 DnD (a drag started from a `<button>` inside a `draggable` row is unreliable across browsers): plain pointer events — `pointerdown` on the grip registers `pointermove`/`pointerup`/`pointercancel` on `document` (plus window `blur`) for the drag's lifetime, `elementFromPoint` picks the row under the cursor and the dragged row goes before/after it depending on which half was crossed. **Never add `setPointerCapture` here**: `insertBefore()` re-inserts the moved row (and its grip) into the DOM, and a re-inserted element loses its capture, so the drag silently died after the first move and left the `masonry-item-dragging`/`masonry-sorting` state stuck — that was the original "drag doesn't work" bug. Known limitation: the drag doesn't auto-scroll the page, so on a long gallery the arrows are the reliable option. The row's controls (grip, arrows, trash) sit *under* the alt-text input in the `col-5` half of the row (`flex-wrap`, trash pushed right with `ms-auto`) so they can't overflow the card at narrow widths. Order is stored purely as the DOM/POST order of `gallery[<index>]` (indices are the original ones and may be out of sequence or `new<n>` for added rows — PHP keeps the body's insertion order and `handleSaveComponent()` re-indexes with `array_values()`), so nothing persists until that tile's "Uložit". `masonry_item` is a child-only type (`PagePresenter::CHILD_ONLY_TYPES`): not in the "Přidat blok" dropdown, rejected at page level or under `columns`. Historical: tiles used to be a JSON `items` list on the masonry component itself (first `{image_url, link_url, alt}`, then "books" with heading/text/gallery); `Version20260914180000` converted them into `masonry_item` rows, `link_url` had no counterpart and was dropped; `contact_form` (heading, action_url, button_text, placeholders) posts `email` + `message` fields to an external `action_url` (e.g. Formspree) and renders nothing without one — it's a raw HTML form, deliberately without CSRF protection since the target is external.

**Image uploads.** `hero.image_url`, `image.url`, and a `masonry_item`'s main image and gallery photos are enhanced client-side (`enhanceImageUpload()`, exported from `assets/admin/image-upload.js`, mounted on `[data-image-upload]` — see the `imageUploadField` Latte define in `_componentEditor.latte`) with drag-and-drop / click-to-browse upload, on top of the plain text input that still works as a manual URL paste. Upload goes through `Admin\BasePresenter::handleUploadImage()` (a generic AJAX signal reachable as `uploadImage!` from *every* admin presenter — Page and Layout both use it — `checkSameSiteRequest()`-guarded like the others; `checkSameSiteRequest()` and the `iniBytes()` helper live in `Admin\BasePresenter` too) to `App\Helpers\ImageUploader`. The masonry screen additionally has bulk dropzones — one at the top (`[data-masonry-bulk-create]`, creates a `masonry_item` per file via `createMasonryItems!`) and one per tile for its gallery (`[data-gallery-bulk]`, appends a gallery row per file), both wired by the same `wireBulkDropzone()` in `assets/admin/masonry.js` — neither gets its own upload endpoint: each uploads the picked files one at a time through the same `uploadImage!` signal (one file per request sidesteps PHP's request-wide `post_max_size`/`max_file_uploads` — only `upload_max_filesize`, which must already cover `ImageUploader::MAX_SIZE`, applies) (`uploadFiles()` + the shared `applyUploadedUrl`/`uploadImage` helpers from `image-upload.js`), collecting per-file failures — including non-image files it skipped without sending — into one message at the end; `uploadImage()` also rejects anything over the 8 MB cap client-side before any request is made. Order: drag & drop keeps the file-manager selection order; a file-dialog `FileList` has no such order so it's sorted alphabetically (`Intl.Collator('cs', {numeric:true})`). `ImageUploader` validates the file by its actual decoded image type (`getimagesize()`, never the client's filename/Content-Type — this is also why SVG is rejected: it's not a GD raster type, so it can never carry an inline-`<script>` XSS payload through here), rejects anything over `ImageUploader::MAX_SIZE` (8 MB — also needs `php.ini`'s `upload_max_filesize`/`post_max_size` to actually allow that, particularly on shared hosting), and stores the file under `www/uploads/<year>/<month>/<webalized-name>-<random-hex>.<ext>` (date-sharded so one directory doesn't accumulate thousands of files). Every successful upload is also recorded in the `uploads` table (`App\Entity\Upload` / `App\Models\UploadManager`) with `AuditColumns` — this is an audit trail and the foundation for a future media library, **not** a foreign key from the content fields above (they just hold the plain returned URL string, same as a hand-pasted external URL would). Nothing currently deletes the underlying file or its `Upload` row when a component/item referencing it is removed — orphaned files are accepted debt until that media-management feature exists, not an oversight. `www/uploads/.htaccess` disables PHP execution in that directory as defense in depth (the type validation above should already make this unreachable). Like `temp/sessions/`, `www/uploads/` is tracked via a committed `.gitkeep` (its contents are gitignored) because Nette/git won't create empty directories on a fresh clone.

`columns` is a **container component** (as is `masonry`, above): components nest one level via `PageComponent::$parent`/`$children` (self-reference, `ON DELETE CASCADE`). Which types may go under which container, and how many, is one map — `PagePresenter::CONTAINER_TYPES` — used by `handleAddComponent()` for both. Each child *is* one column — the front renderer puts every visible child in an equal-width `.col-md` in one row; `sortOrder` within the parent is the left-to-right order. Allowed child types: heading/text_block/cta/image (no nested containers), at most 4 children — both from `CONTAINER_TYPES['columns']`. In the page editor the columns card is compact (count + "Upravit sloupce" button); columns are managed on a dedicated screen, `Admin:Page:columns/<componentId>` (`actionColumns` + `columns.latte`), where children are added/reordered/removed. Page-level iteration must use `Page::getRootComponents()` (children render via their parent); child iteration and counting must use `PageComponent::getActiveChildren()` (raw `getChildren()` includes soft-deleted rows and is only for collection management); the front renderer is a recursive `{define renderComponent}` block in `components.latte`. Deleting a container soft-deletes its children with it. `edit.latte` and `columns.latte` share `{define componentHeader/componentForm}` from `_componentEditor.latte` (via `{import}`); `componentHeader` takes `horizontal: true` on the columns screen to show left/right arrows (the `moveComponent!` direction stays up/down). An older flat `two_cols_text` type was removed; existing ones were converted into `columns` containers with two `text_block` children (the conversion migration now lives only in git history — see the squashed baseline).

Front page structure follows the design PDF: a white page (`$body-bg`; front only — the admin palette overrides it) with one inset gray panel, `.site-canvas` (header + `<main>`, `$canvas-bg`, `$panel-inset` = 3vw from the viewport edges on top and both sides); the studio header, masonry grid and tile book view (`.book-frame`) all use the shared `$wide-width` (`front/_layout.scss`: `min($wide-max-width, 100vw − 2 × $panel-inset − 3rem)`, i.e. at most 1290px and always inside the panel) so their left edges line up; the page ends with the footer's carousel, full-bleed on white below the panel. Navbars and footers are **not** page components: they are reusable `LayoutBlock` entities (`layout_blocks`, type `nav` or `footer`), managed centrally under `Admin:Layout` ("Navigace a patičky" in the sidebar) and assigned to pages via the `Navigace`/`Patička` dropdowns in the page settings form (`Page::$navBlock`/`$footerBlock`, `SET NULL` FKs). `Front/@layout.latte` renders the assigned blocks in the navbar/footer regions (`$page` is set only by Page:default and the selected-homepage Home:default). **There are no defaults**: a page without assigned blocks (and every non-CMS front page, e.g. Auth) renders no navbar/footer at all, and the front must never link to the admin section or login — visitors are not supposed to know it exists. `nav` content is `style` — `LayoutBlock::STYLE_STUDIO` (logo + small vertical link list, `.site-header`, as wide as the masonry grid via the shared `$wide-width` so their left edges line up) or `STYLE_NAVBAR` (classic Bootstrap navbar); new blocks default to studio, blocks without the key are navbars (`LayoutBlock::getStyle()`) — plus `brand` — the brand text, falling back to "Kobra" when empty, and the logo's alt — plus `logo_url` — optional uploaded logo shown instead of the brand text in both styles (the shared `imageUploadField` widget, read from the raw POST like the footer carousel; the nav form in `Layout/edit.latte` is therefore rendered by hand) — plus `links`, plain multiline text, one `Text | URL` link per line, parsed by `App\Helpers\LinkList` (`LayoutBlock::getLinks()`, `Menu::getLinks()`) and auto-escaped; Nette renders the `style` select as `name="_style"` (reserved DOM form property) — `$data->style` is unaffected, but a hand-built POST must use `_style`; `footer` content is `text` — a rich-text field sanitized in `LayoutPresenter` — plus an optional `carousel`: a list of `{image_url, alt, link_url}` rows rendered above the text as an **endless image marquee** (a strip of logos/covers; a row with a non-empty `link_url` is an `<a>`, otherwise a `<div>`). The footer form is rendered by hand in `Admin/Layout/edit.latte` (`<form n:name>` + `{input}`s) so the carousel rows — the shared `imageListEditor` from `Admin/Page/_componentEditor.latte`, which the template `{import}`s, with `withLink: true` — sit inside the `<form>` as plain inputs; they are not Nette form controls, so `blockFormSucceeded()` reads them from the raw POST (`carousel[<index>][image_url|alt|link_url]`, body order = display order, normalized by `LayoutPresenter::carouselItems()`, rows without an image dropped). The nav form keeps `{control blockForm}`. Front rendering is in `Front/@layout.latte`: pure CSS, the track repeats the slides `$copies` times (`max(2, ceil(12 / count))`, so a handful of slides still outruns the viewport) and the keyframe slides it by exactly one copy (`translateX(-100% / var(--carousel-copies))`), which is what makes the loop seamless; duration is `3 s × slides × copies`, computed in Latte into an inline `--carousel-duration` (inline CSS custom props are fine — the no-hardcoded-colors rule is about colors). The animation is written as **longhands** in `front/_layout.scss` (`.footer-carousel*`) because Chrome drops the `animation` shorthand when its duration is a `calc()`/`var()`. Repeats after the first carry `aria-hidden` (+ `tabindex=-1` on links); the strip pauses on hover, fades at both edges via `mask-image`, spans the full viewport width, and **deliberately ignores `prefers-reduced-motion`** (macOS "Reduce motion" is on for many people without them knowing, and a non-rolling strip looked like a bug — hover-to-pause is the escape hatch; the book-view animations in `.masonry-book-modal` do respect it). Image height is fixed (`$carousel-height`, 111px), width follows the aspect ratio; slides sit almost edge to edge (`$carousel-gap`, .15rem) at full opacity — the design expects equal-size square images (the logo padded inside), so logos keep their relative size. A footer renders when it has text *or* at least one carousel image. Soft-deleting a block leaves pages' FKs in place; `Page::getNavBlock()`/`getFooterBlock()` return null for deleted blocks, so those pages just stop showing them. Nav blocks can additionally include **menus** (`Menu` entity, `menus` table, managed under `Admin:Menu`): a menu is a named `Text | URL` link list; the nav-block form offers them as a checkbox list (M:N via `layout_block_menus`), and the front renders each assigned menu as a Bootstrap dropdown labelled with the menu name (requires `bootstrap/js/dist/dropdown` in `front.js`; the navbar collapses into the hamburger below md as before). `LayoutBlock::getActiveMenus()` filters soft-deleted menus, so deleting a menu just removes the dropdown from every navbar using it. (Historical: nav/footer used to be per-page component types before being converted into layout blocks; that conversion migration lives only in git history.)

Text fields fall into two classes. **Rich-text fields** — `text_block.content`, `cta.body`, and `footer.text` — store sanitized HTML: the admin edits them with a Quill WYSIWYG editor (mounted on `textarea[data-richtext]`, `assets/admin/richtext.js`), and `handleSaveComponent()` runs every posted value through `App\Helpers\RichTextSanitizer` (HTMLPurifier with a strict allowlist — bold/italic/underline/strike, links, lists, blockquote; no headings, since the dedicated `heading` component type owns page heading structure) before persisting; empty content is normalized to `''`. These are rendered with `|noescape` in `components.latte` — safe only because they are always sanitized server-side on save, never trust unsanitized HTML here. **Plain-text fields** — every single-line field (`hero.heading`/`subheading`/`button_text`, `heading.text`, `cta.heading`/`button_text`, `image.url`/`alt`/`caption`, every `contact_form` key, `nav.brand`, a `masonry_item`'s `main_image_alt`/`heading` and each gallery photo's `alt`) plus the multiline `nav.links` and `masonry_item.text` — remain plain `<input>`/`<textarea>` values and stay auto-escaped (Latte default; `text` additionally goes through the built-in `|breakLines` filter so its line breaks render, still fully escaped — never `|noescape` those). URL-ish content keys (`image.url`, `hero.image_url`, `contact_form.action_url`, button URLs, a `masonry_item`'s `main_image_url` and gallery `image_url`, `nav.logo_url`) are covered by Latte's built-in `src`/`href`/`action` URL sanitization — keep them in those attributes.

## Assets

Two Vite entries (`vite.config.ts` → `@nette/vite-plugin`): `assets/admin.js` and `assets/front.js`, referenced in layouts via `{asset 'admin.js'}` / `{asset 'front.js'}` (nette/assets emits both script and CSS links from the manifest). `admin.js` is a thin entry — vendor imports + `netteForms.initOnLoad()` + `initRichText()`/`initImageUploads()`/`initMasonry()` — with the page-editor widgets split into `assets/admin/{richtext,image-upload,masonry}.js` (`masonry.js` reuses `image-upload.js`'s exported `enhanceImageUpload`, `wireDropzone`, `spinnerOverlay`, `applyUploadedUrl`, `uploadImage`). Everything is self-hosted/bundled — no CDN links. Bootstrap is compiled from Sass with theme overrides in `assets/scss/_theme.scss` (radii, shadows, fonts). **Every color lives in `assets/scss/_colors.scss`** — Bootstrap overrides (`$primary`, `$body-bg`, …), extra hues, and the named front/admin colors (hero, CTA, sidebar, component-type accents, dropzone); `_theme.scss` imports it before Bootstrap. The admin bundle has its own palette: `admin.scss` imports `_colors-admin.scss` first, which overrides the `!default` base values (so new base colors need `!default`; derived ones don't). Never hardcode a hex/`rgba()` in a layout SCSS file or template — add a named variable to `_colors.scss` and use it (only Sass functions available before Bootstrap loads — `rgba`, `mix`, `darken` — work there).

Datagrid AJAX: `admin.js` imports `@contributte/datagrid/dist/datagrid-full.js`, which bundles **and initializes** naja, nette-forms wiring and Bootstrap's Dropdown data-API. Do not import `bootstrap` wholesale in `admin.js` (dropdowns would toggle twice); import individual modules like `bootstrap/js/dist/alert` instead. AJAX signal handlers in presenters follow the pattern: `if ($this->isAjax()) { $this->redrawControl('flashes'); $this['grid']->reload(); } else { $this->redirect('this'); }` — the admin layout wraps flashes in `{snippet flashes}` for this.

## Gotchas

- macOS Homebrew PHP's default `php.ini` (`/opt/homebrew/etc/php/8.2/php.ini`) ships `upload_max_filesize = 2M` — comfortably below a typical phone photo (3+ MB) and below `ImageUploader::MAX_SIZE` (8 MB). PHP rejects the upload itself before `ImageUploader` ever runs, and there are two different symptoms: over `upload_max_filesize` the file still arrives, just with `FileUpload::isOk()` false (`getError()` = `UPLOAD_ERR_INI_SIZE`/`UPLOAD_ERR_FORM_SIZE`, worded in `ImageUploader::upload()`); over `post_max_size` PHP drops `$_FILES` *and* `$_POST` wholesale, so nothing arrives at all — `PagePresenter::handleUploadImage()` detects that case by comparing the request's `Content-Length` with `ini_get('post_max_size')` and words it too (otherwise the admin would be told they sent no file). With `display_errors` on (the `php -S` dev default), PHP additionally prints its own warning *before* the JSON, which breaks the widget's `response.json()` — production has it off. Bump `upload_max_filesize`/`post_max_size` locally and restart `php -S` (it doesn't reload `php.ini` while running) if uploads mysteriously fail on real photos.
- `temp/sessions/` (the `session.savePath` in `common.neon`) is not created by Nette itself — it only exists in git as a tracked `.gitkeep` (see `temp/.gitignore`). A fresh clone/copy without that file, or with the directory wiped, fails at runtime with "Failed to read session data: files (path: .../temp/sessions)"; create it and make it writable.
- `parameters.database.port` (`config/common.neon`) is a real, overridable parameter (used in both the Doctrine DBAL connection and the legacy Nette Database DSN) — not hardcoded to 3306, so a local MariaDB/MySQL on a non-default port works via `config/local.neon`.
- On macOS with Homebrew, don't run `brew services start mariadb@10.11` for local MariaDB dev — that formula's service block hardcodes the same datadir as the `mysql` formula, so it collides with any native Homebrew `mysql` install on the machine. Use `bin/mariadb-dev start|stop|status` instead: it runs the same Homebrew-installed `mariadbd` binary directly against its own datadir and port 33061, independent of `brew services`.
- Form component names are camelCase (`userName`, not `username`); Latte `{input username}` on a form with `userName` throws at render time.
- `FormFactory` has three explicit methods — `createLoginForm()`, `createRegisterForm()`, `createUserForm(User $user)` — sharing field-building via private `addPersonalFields()`/`addPasswordField()` helpers. All form labels/messages are constants on `App\Helpers\FormHelper`.
- The datagrid PHP package is `ublaboo/datagrid` v7 but its namespace is `Contributte\Datagrid`, and the matching JS/CSS npm package is `@contributte/datagrid`.
- Datagrid's internal icons use Font Awesome (`fas fa-`), while the app's own icons are Bootstrap Icons (`bi bi-`); both fonts are bundled in `admin.js` on purpose. Consequently, datagrid `setIcon()` takes a **bare FA name without any prefix** (`setIcon('pencil')` → `fas fa-pencil`): the grid prepends `fas fa-` to *every space-separated word*, so `setIcon('bi bi-house')` renders the broken `fas fa-bi fas fa-bi-house`. Check the icon exists in the bundled Font Awesome 6 free set (`node_modules/@fortawesome/fontawesome-free/css/all.min.css`) — e.g. there is no `fa-house-slash`; use `house-circle-xmark`.
- The component-editor forms in `edit.latte` are raw HTML posting to signals, so they carry no Nette Form CSRF token. `Admin\Page\PagePresenter`'s `handleAddComponent()`/`handleSaveComponent()`/`handleDeleteComponent()` guard against this manually via a private `checkSameSiteRequest()` that checks `getHttpRequest()->isSameSite()` (the same SameSite-cookie mechanism `Nette\Application\UI\Form` uses internally). Add that call to any new signal handler reachable from `edit.latte`.
- `www/assets/` is build output and gitignored; never edit files there.
- `bin/console` runs in non-debug mode, so Nette does **not** recompile the DI container when config *content* changes — after editing/creating/removing `config/local.neon`, delete `temp/cache/nette.configurator/` (or the console silently keeps using the old DB credentials baked into the cached container).
- `%wwwDir%` is pinned explicitly in `App\Bootstrap` (`addStaticParameters(['wwwDir' => …/www])`). Nette otherwise derives it from the *entry script's* directory, so it would be `www/` under `www/index.php` but `bin/` under `bin/console` — and any service building filesystem paths from it (`ImageUploader(%wwwDir%/uploads)` in `services.neon`) would silently write outside the web root when run from a console command. Don't remove the pin; if you add another path-based service, use `%wwwDir%`/`%appDir%`/`%tempDir%` rather than re-deriving from `__DIR__`.
- Never run `orm:schema-tool:update` (with or without `--force`) against this DB — it's not part of the supported workflow (only `migrations:diff` / `migrations:migrate` / `orm:validate-schema` are) and it's destructive: it drops any table not backed by an ORM entity, including `doctrine_migrations` itself. A `schemaAssetsFilter` used to hide that table from schema-tool as a safety net, but it also hid the table from Doctrine Migrations' own `TableMetadataStorage` (same shared DBAL connection), which broke `migrations:status`/`migrate` (reported 0 executed migrations, then "table already exists" on migrate). The filter was removed for that reason — use the migrations workflow exclusively instead of relying on a filter to make schema-tool safe.
- Migration files carry no explanatory docblocks, so the conventions live here. Baseline (`Version20260904120000`): booleans are `TINYINT(1)` everywhere (Doctrine's `boolean` type), every table is explicitly InnoDB / `utf8mb4` / `utf8mb4_unicode_ci`, and `content` columns are native `JSON` — on MariaDB 10.4.3+ that's a `LONGTEXT` alias with a `json_valid()` CHECK, which DBAL's MariaDBPlatform emits and introspects as JSON, so it matches the `type: 'json'` mapping and `orm:validate-schema` stays clean. `Version20260904152113` only adds the `uploads` table. Data migrations (`Version20260914180000`, masonry `items` → `masonry_item` rows) read through `$this->connection` directly but queue every write with `addSql()` — Doctrine's `--dry-run` skips only the queued SQL, not the `up()` body, so writing through the connection would make a dry run mutate data. Follow that pattern for any new data migration.
